# 02 — Golden Paths

> **Purpose:** A golden path is not a restriction — it is a gift. It is the result of the
> platform team having already solved every tedious problem a new subgraph team would otherwise
> spend weeks on: project scaffolding, CI wiring, OTel bootstrapping, DataLoader setup, Dockerfile
> tuning, and Helm values configuration. This document defines what the GraphQL golden path
> contains, how it is delivered via CLI and Backstage, and how it stays current as platform
> standards evolve without requiring product teams to manually migrate.

---

## What a Golden Path Is

The term "golden path" (sometimes "paved road") originates from Netflix's internal platform
engineering culture. A golden path has a precise definition:

**An opinionated, well-lit trail that makes the right thing easy and the wrong thing visible.**

It has three structural properties:

1. **Opinionated.** A golden path makes choices. It does not present ten ways to set up a
   TypeScript GraphQL subgraph and ask the developer to pick. It presents one way — the one
   that the platform team has validated, secured, and can support — and makes it trivially
   easy to use.

2. **Well-lit.** Deviations from the golden path surface immediately: as CI failures, lint
   errors, or explicit platform warnings. A developer who removes the OTel bootstrap from
   a golden-path-generated subgraph sees a CI failure explaining exactly what was removed
   and why it is required.

3. **Easy.** The total time to follow the golden path — from "I want a new subgraph" to
   "my first schema check is passing in CI" — must be shorter than any reasonable alternative.
   If the golden path takes two hours and doing it manually takes three, developers will
   use the golden path. If the golden path requires filing four tickets and takes two weeks,
   developers will bypass it.

### What a Golden Path Is Not

- It is not a restriction framework. Developers can always leave the golden path. The
  platform team documents the off-ramp process (usually an RFC or exception request) and
  communicates what operational support they will and will not provide for non-golden-path
  configurations.

- It is not a one-time artifact. A golden path generated in 2023 using Apollo Federation v1
  and Node.js 18 is technical debt in 2025. Golden paths are living products with version
  numbers and migration tooling.

- It is not a compliance checkpoint. The golden path CI hooks enforce correctness, not
  bureaucratic review. No human approval is required to start a new subgraph on the
  golden path.

## The GraphQL Golden Path Stack

The golden path for a new GraphQL subgraph includes the following components, all
generated by the scaffold tool and pre-configured to work together:

```
graphql-golden-path/
├── Runtime Stack
│   ├── TypeScript + Node.js 22 (or Kotlin/Spring Boot for JVM teams)
│   ├── Apollo Server 4 with Apollo Federation v2
│   ├── graphql-tag for SDL parsing
│   └── DataLoader for batched resolver patterns
│
├── Observability Stack
│   ├── @opentelemetry/sdk-node (traces + metrics)
│   ├── @opentelemetry/exporter-otlp-grpc
│   ├── pino (structured JSON logging)
│   └── prom-client (Prometheus metrics endpoint)
│
├── Schema Governance Stack
│   ├── graphql-eslint (.eslintrc with required rules)
│   ├── @graphql-inspector/core (local schema diff)
│   └── pre-commit hook (local schema check before push)
│
├── CI Stack
│   ├── GitHub Actions workflow (.github/workflows/schema-check.yml)
│   ├── GitHub Actions workflow (.github/workflows/deploy.yml)
│   └── Rover CLI pinned version
│
├── Infrastructure Stack
│   ├── Dockerfile (multi-stage, non-root user, health check)
│   ├── helm/values.yaml (resource limits, probes, PDB)
│   └── router-fragment.yaml (router URL registration)
│
└── Developer Experience Stack
    ├── docker-compose.local.yml (local supergraph composition)
    ├── .devcontainer/devcontainer.json (VS Code devcontainer)
    └── .vscode/extensions.json (recommended extensions)
```

## CLI Tool: `graphql-platform`

The primary delivery mechanism for the golden path is the `graphql-platform` CLI.
It is distributed as a binary (Go, cross-platform) and as a Docker image for CI use.

### Installation

```bash
# macOS (Homebrew)
brew install myorg/tap/graphql-platform

# Linux (curl install)
curl -fsSL https://platform.internal.myorg.com/install.sh | sh

# Docker (CI use)
docker pull registry.internal.myorg.com/graphql-platform:latest
```

### Creating a New Subgraph

```bash
graphql-platform new-subgraph \
  --name products \
  --team catalog \
  --description "Product catalog domain — search, details, pricing" \
  --language typescript \
  --github-org myorg
```

### Additional Commands

```bash
# Check if a subgraph's scaffold is up to date with the latest golden path
graphql-platform check-drift --subgraph products-subgraph

# Apply golden path updates to an existing subgraph
graphql-platform update --subgraph products-subgraph --from-version 1.4 --to-version 1.7

# List all registered subgraphs and their golden path versions
graphql-platform list-subgraphs

# Validate a subgraph's configuration against current platform policies
graphql-platform validate --subgraph products-subgraph
```

## Backstage Software Templates (Alternative to CLI)

For organizations already running Backstage, the golden path is delivered as a
[Software Template](https://backstage.io/docs/features/software-templates/) rather than
(or in addition to) the CLI. Backstage templates provide a web UI for teams that prefer
forms over terminals, and they integrate with the Backstage catalog natively.

### Template Definition

```yaml
# backstage/templates/graphql-subgraph/template.yaml
apiVersion: scaffolder.backstage.io/v1beta3
kind: Template
metadata:
  name: graphql-subgraph
  title: GraphQL Subgraph
  description: |
    Creates a new Apollo Federation subgraph with CI, observability,
    infrastructure provisioning, and schema registry registration.
  tags:
    - graphql
    - subgraph
    - platform
spec:
  owner: graphql-platform-team
  type: service

  parameters:
    - title: Subgraph Details
      required:
        - subgraphName
        - teamName
        - description
      properties:
        subgraphName:
          title: Subgraph Name
          type: string
          description: Lowercase, hyphenated (e.g., products, user-preferences)
          pattern: '^[a-z][a-z0-9-]{2,30}$'
        teamName:
          title: Owning Team
          type: string
          description: Team name in Backstage (must exist in catalog)
          ui:field: OwnerPicker
          ui:options:
            catalogFilter:
              kind: Group
        description:
          title: Description
          type: string
          description: One sentence describing what domain this subgraph serves
        language:
          title: Language
          type: string
          enum:
            - typescript
            - kotlin
            - go
          default: typescript

    - title: Infrastructure
      properties:
        environment:
          title: Initial Environments
          type: array
          items:
            type: string
            enum: [staging, production]
          default: [staging, production]
        resourceTier:
          title: Resource Tier
          type: string
          enum: [small, medium, large]
          default: small
          description: |
            small: 100m CPU / 256Mi RAM
            medium: 500m CPU / 1Gi RAM
            large: 1000m CPU / 2Gi RAM

  steps:
    - id: fetch-template
      name: Fetch Subgraph Template
      action: fetch:template
      input:
        url: ./skeleton
        values:
          subgraphName: ${{ parameters.subgraphName }}
          teamName: ${{ parameters.teamName }}
          description: ${{ parameters.description }}
          language: ${{ parameters.language }}
          resourceTier: ${{ parameters.resourceTier }}

    - id: publish-github
      name: Publish to GitHub
      action: publish:github
      input:
        allowedHosts: ['github.com']
        repoUrl: github.com?owner=myorg&repo=${{ parameters.subgraphName }}-subgraph
        defaultBranch: main
        branchProtection: true

    - id: provision-infrastructure
      name: Provision Kubernetes Infrastructure
      action: http:backstage:request
      input:
        method: POST
        path: /api/platform/provision-subgraph
        body:
          subgraphName: ${{ parameters.subgraphName }}
          teamName: ${{ parameters.teamName }}
          resourceTier: ${{ parameters.resourceTier }}
          repoUrl: ${{ steps['publish-github'].output.remoteUrl }}

    - id: register-catalog
      name: Register in Backstage Catalog
      action: catalog:register
      input:
        repoContentsUrl: ${{ steps['publish-github'].output.repoContentsUrl }}
        catalogInfoPath: /catalog-info.yaml

  output:
    links:
      - title: Repository
        url: ${{ steps['publish-github'].output.remoteUrl }}
      - title: Schema Registry
        url: https://studio.apollographql.com/graph/myorg-supergraph
      - title: Platform Docs
        url: https://platform.internal.myorg.com/docs/new-subgraph
```

## Scaffold Contents: File-by-File

### `src/index.ts` — Entry Point with OTel Bootstrap

The OTel SDK must be initialized before any other module imports. The scaffold generates
a dedicated bootstrap file to enforce this:

```typescript
// src/telemetry.ts — must be the first import in index.ts
import { NodeSDK } from '@opentelemetry/sdk-node';
import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-grpc';
import { OTLPMetricExporter } from '@opentelemetry/exporter-metrics-otlp-grpc';
import { PeriodicExportingMetricReader } from '@opentelemetry/sdk-metrics';
import { Resource } from '@opentelemetry/resources';
import { SEMRESATTRS_SERVICE_NAME, SEMRESATTRS_SERVICE_VERSION } from '@opentelemetry/semantic-conventions';

const sdk = new NodeSDK({
  resource: new Resource({
    [SEMRESATTRS_SERVICE_NAME]: process.env.OTEL_SERVICE_NAME ?? 'products-subgraph',
    [SEMRESATTRS_SERVICE_VERSION]: process.env.npm_package_version ?? '0.0.0',
  }),
  traceExporter: new OTLPTraceExporter({
    url: process.env.OTEL_EXPORTER_OTLP_ENDPOINT ?? 'http://otel-collector:4317',
  }),
  metricReader: new PeriodicExportingMetricReader({
    exporter: new OTLPMetricExporter({
      url: process.env.OTEL_EXPORTER_OTLP_ENDPOINT ?? 'http://otel-collector:4317',
    }),
    exportIntervalMillis: 60_000,
  }),
});

sdk.start();

process.on('SIGTERM', () => {
  sdk.shutdown().finally(() => process.exit(0));
});
```

```typescript
// src/index.ts
import './telemetry';  // Must be first import

import { ApolloServer } from '@apollo/server';
import { startStandaloneServer } from '@apollo/server/standalone';
import { buildSubgraphSchema } from '@apollo/subgraph';
import { typeDefs } from './schema';
import { resolvers } from './resolvers';
import { createContext } from './context';
import { logger } from './logger';

const server = new ApolloServer({
  schema: buildSubgraphSchema({ typeDefs, resolvers }),
  plugins: [
    // Health check endpoint for Kubernetes probes
    {
      async serverWillStart() {
        return {
          async drainServer() {
            logger.info('Server draining — Kubernetes SIGTERM received');
          },
        };
      },
    },
  ],
});

const { url } = await startStandaloneServer(server, {
  listen: { port: parseInt(process.env.PORT ?? '4001', 10) },
  context: createContext,
});

logger.info({ url }, 'Subgraph server started');
```

### `src/dataloader.ts` — DataLoader Setup

```typescript
// src/dataloader.ts
import DataLoader from 'dataloader';
import { ProductRepository } from './repositories/product.repository';

export interface DataLoaders {
  productById: DataLoader<string, Product | null>;
  productsByCategory: DataLoader<string, Product[]>;
}

export function createDataLoaders(repo: ProductRepository): DataLoaders {
  return {
    productById: new DataLoader(
      async (ids: readonly string[]) => {
        const products = await repo.findByIds([...ids]);
        const productMap = new Map(products.map(p => [p.id, p]));
        // DataLoader requires results in the same order as keys
        return ids.map(id => productMap.get(id) ?? null);
      },
      {
        maxBatchSize: 100,
        cacheKeyFn: (key) => key,
      }
    ),

    productsByCategory: new DataLoader(
      async (categoryIds: readonly string[]) => {
        const results = await repo.findByCategoryIds([...categoryIds]);
        const grouped = new Map<string, Product[]>();
        for (const product of results) {
          const list = grouped.get(product.categoryId) ?? [];
          list.push(product);
          grouped.set(product.categoryId, list);
        }
        return categoryIds.map(id => grouped.get(id) ?? []);
      },
      { maxBatchSize: 50 }
    ),
  };
}
```

### `Dockerfile` — Multi-Stage, Non-Root

```dockerfile
# Dockerfile
FROM node:22-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci --ignore-scripts
COPY tsconfig.json ./
COPY src/ ./src/
RUN npm run build

FROM node:22-alpine AS runtime
WORKDIR /app

# Non-root user for security
RUN addgroup -S appgroup && adduser -S appuser -G appgroup

COPY package*.json ./
RUN npm ci --only=production --ignore-scripts && npm cache clean --force

COPY --from=builder /app/dist ./dist

USER appuser

EXPOSE 4001

# Kubernetes liveness/readiness probe endpoint
HEALTHCHECK --interval=10s --timeout=5s --start-period=30s --retries=3 \
  CMD wget -qO- http://localhost:4001/.well-known/apollo/server-health || exit 1

CMD ["node", "dist/index.js"]
```

## Keeping Golden Paths Up to Date

The golden path is a product. It has a version number (`graphql-platform-template@1.7.0`),
a changelog, and a migration path between versions. Without active maintenance, the golden
path becomes a liability: subgraphs generated from old templates run outdated Node.js
versions, use deprecated APIs, and miss new security requirements.

### Template Versioning

The scaffold template is versioned using semantic versioning:

- **Patch** (1.7.0 → 1.7.1): Security patches, dependency updates, documentation fixes.
  Applied automatically by Dependabot PRs in each subgraph.
- **Minor** (1.7.0 → 1.8.0): New optional features added to the scaffold (e.g., adding
  a new observability integration). Existing subgraphs receive an automated PR with the
  change, which teams can merge at their convenience.
- **Major** (1.7.0 → 2.0.0): Breaking changes to the template structure (e.g., migration
  from CommonJS to ESM, Apollo Server 3 to 4). A migration guide is published and teams
  have a 90-day window to migrate before the old version loses platform support.

### Automated Drift Detection and PRs

The `graphql-platform check-drift` command (and its CI equivalent) compares a subgraph's
current scaffold state against the latest golden path version. When drift is detected,
an automated PR is created:

```yaml
# .github/workflows/platform-drift-check.yml
# This workflow runs in the PLATFORM team's repository
# and opens PRs in each registered subgraph
name: Golden Path Drift Check

on:
  schedule:
    - cron: '0 9 * * 1'  # Monday 9am — weekly check
  workflow_dispatch:

jobs:
  check-all-subgraphs:
    runs-on: ubuntu-latest
    steps:
      - name: List registered subgraphs
        id: list
        run: |
          graphql-platform list-subgraphs --format json > subgraphs.json

      - name: Check and open drift PRs
        run: |
          graphql-platform update-all \
            --subgraphs-file subgraphs.json \
            --template-version latest \
            --open-prs \
            --pr-title "chore: apply graphql-platform template v${{ env.TEMPLATE_VERSION }}" \
            --pr-label "platform-update"
```

Each automated PR includes:
- A diff of exactly what changed in the template
- The changelog entry for the new template version
- A link to the migration guide if manual steps are required
- A deadline comment for major version updates
